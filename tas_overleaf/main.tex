\begin{abstract}
Evaluating a multi-step agent spans several layers --- model provider, tool
runtime, mutable environment, trajectory logger, and benchmark evaluator --- and
an error crossing a boundary between them can silently change which scientific
variable is recorded without ever crashing the experiment. We report five
controlled cases from an instrumented coding-agent harness in which a defensible
implementation choice corrupts a behavioural feature, a ground-truth outcome, or
a validity judgement. In one, a command touching no repository file moves a
container-wide change count from 0 to 32 while the repository-scoped measurement
correctly stays at 0; in another, 20 adversarial future steps alter 0 of 24
online features once the temporal boundary is enforced. We argue these share one
pathology, cross-layer confounding, and respond with a three-channel measurement
architecture, an operational validity contract governing when a task label may
be assigned, and an artifact enforcing nine invariants as regression tests.
Results are preliminary and methodological: they establish that such failures
are possible and cheaply preventable, not how often they occur.
\end{abstract}

\section{Introduction}

When does an agent execution constitute valid evidence about the agent?

Agent evaluation increasingly studies reliability, failure trajectories,
recovery, routing, and resource use. Every one of these analyses presupposes two
things: that what is recorded as agent behaviour actually originated from the
agent, and that what is recorded as task failure is actually a valid task
outcome. Neither is automatic. If a benchmark cannot distinguish an agent
failure from an infrastructure failure, its reliability estimate is itself
unreliable.

Multi-step agents make this fragile in a specific way. A single-turn benchmark
compares one model output to one reference. An agentic evaluation instead
threads \emph{model $\rightarrow$ tool $\rightarrow$ environment $\rightarrow$
model $\rightarrow$ evaluation}, repeatedly, through components never designed
as measurement apparatus: a shell, a container filesystem, a rate-limited HTTP
API, and a test runner. Each hand-off is a place where the quantity recorded can
drift from the quantity claimed, and the drift is rarely loud. A pipeline
returns $0$; a file counter returns a large number; an evaluator reports ``no
failures.'' None looks like a bug.

We call the underlying pathology a \textbf{cross-layer measurement confound}: an
event or state originating outside the semantic quantity being measured is
recorded as evidence about that quantity. The term is descriptive, not novel; we
use it only as the organizing abstraction for five case studies.

\vspace{2pt}
\noindent\textbf{Threat model.} We study \emph{accidental} measurement-integrity
failures in a multi-layer evaluation stack. We do not study malicious benchmark
manipulation, model safety attacks, training contamination, or the population
prevalence of these defects. The relevant threat is an evaluation pipeline that
appears to succeed while silently recording the wrong scientific variable.

\vspace{2pt}
\noindent\textbf{Contributions.}
\begin{itemize}\itemsep1pt \parskip0pt \topsep2pt
\item \textbf{Five controlled demonstrations} of cross-layer confounds in
agentic coding evaluation, each reproduced from a released artifact with no paid
API access (Section~\ref{sec:cases}).
\item \textbf{A three-channel measurement architecture} and an operational
validity contract defining when a task label may be assigned
(Sections~\ref{sec:model} and~\ref{sec:arch}).
\item \textbf{A reproducible artifact} enforcing nine validity invariants as
regression tests, plus a minimum validity record we offer for discussion
(Section~\ref{sec:arch}).
\end{itemize}

\section{A Measurement Integrity Model}
\label{sec:model}

We model an agentic evaluation as three channels that must not leak into one
another.

\noindent\textbf{Online trajectory ($\mathcal{O}_t$).} Everything knowable at
step $t$: commands, exit statuses, output sizes, token counts, repository state.
Online behavioural features --- the inputs to any deployable monitor or
early-abort policy --- must be computable from $\mathcal{O}_t$ alone. If a
feature can see step $t{+}1$ or the final outcome, a reported ``early
prediction'' is partly a readout of the answer.

\noindent\textbf{Provider telemetry ($\mathcal{P}$).} Physical API attempts,
HTTP 503s, timeouts, quota events, infrastructure termination reasons. These
describe the \emph{service}, not the agent. A retried 503 is not a reasoning
error, and a run killed by a quota limit is not a task failure.

\noindent\textbf{Offline evaluation ($\mathcal{E}$).} The benchmark verdict $Y$,
computed in a clean state from official test data after the agent has stopped.
$Y$ must never be visible to $\mathcal{O}_t$.

Two directed constraints follow: $\mathcal{E} \not\rightarrow \mathcal{O}_t$ (no
outcome leakage) and $\mathcal{P} \not\rightarrow \mathcal{O}_t$ as
\emph{semantics} (infrastructure events may be logged, never treated as agent
behaviour). Figure~\ref{fig:arch} shows the architecture.

\vspace{3pt}
\noindent\fbox{\parbox{0.96\columnwidth}{\small
\textbf{Operational validity contract.} A run $r$ is \emph{valid} when four
conditions hold jointly. \textbf{Temporal:} its online measurements contain only
information available at the measurement point, excluding future and final
outcomes. \textbf{Infrastructure:} it terminated through a scientifically valid
agent path, not a provider or runtime failure. \textbf{Evaluator:} its outcome
came from the correctly configured, isolated offline evaluator.
\textbf{Provenance:} its raw trajectory, state, and accounting artifacts are
immutable and traceable to their execution identity. We assign
$Y_{\text{success}}(r)$ \emph{only} when all four hold. This is the validity
assumption our artifact implements and enforces --- not a theorem, and not a
complete definition of evaluation validity.}}

\section{Failure Cases}
\label{sec:cases}

We instrumented a coding-agent harness (mini-SWE-agent scaffold, SWE-bench
Verified instance, containerised execution) and recorded cases where a natural
implementation choice silently corrupts a measured quantity.
Table~\ref{tab:cases} gives each case, the layer the confound originates in, the
scientific quantity it corrupts, and the measured evidence. All values are
regenerated by one command; E1--E3 use a local container with no model
inference, E4--E5 are pure Python.

\noindent\textbf{E1 (evaluator $\rightarrow$ ground truth).} SWE-bench
\texttt{FAIL\_TO\_PASS} ids often name parametrisations existing only
\emph{after} the official \texttt{test\_patch} is applied. Without it, pytest
exits 4 with ``no tests ran''; with it, exit 1 and 1 failed. Both arms report
$\text{success}=\text{false}$, so a flag check sees nothing wrong --- but the
first arm's ``0 failures'' is vacuous, and any consumer reading
absence-of-failure as passing emits false successes.

\noindent\textbf{E2 (tool runtime $\rightarrow$ behavioural signal).} Agents
pipe constantly. Without \texttt{set -o pipefail} a POSIX shell reports the last
stage's status, so a failing command piped into \texttt{tail} is recorded as a
successful tool call and every failure-rate feature is biased toward zero
exactly when the agent is struggling.

\noindent\textbf{E3 (environment $\rightarrow$ progress measurement).} Counting
modified files with \texttt{docker diff} attributes the whole container to the
agent. A command touching \emph{no} repository file moves that count from 0 to
32 while the repository-scoped git measurement stays at 0; one real source edit
then moves the container count to 33 --- indistinguishable from noise --- while
git moves to exactly 1 file, 2 lines.

\noindent\textbf{E4 (future/oracle $\rightarrow$ online feature).} We compute
features from a length-$k$ prefix, then append 20 maximally predictive future
steps (exit 127, \texttt{FATAL} output, $10^6$ tokens). Across 24 online
features, 0 change; reading at or beyond the cut raises
\texttt{PrefixBoundaryError} and the prefix exposes no outcome attribute. This
is an adversarial regression test, not a proof: it shows the path is closed by
construction rather than convention.

\noindent\textbf{E5 (infrastructure $\rightarrow$ task label).} Enumerating all
termination reasons, the three classified as provider infrastructure
(unavailable, timeout, rate-limited) are structurally refused a $Y$ label by a
schema validator; the five agent-semantic reasons accept one; 0 violations. This
was not hypothetical for us. Eight provider-backed sessions on one free-tier
account (two parent runs executing 9 and 4 agent steps, plus six continuations
restored from parent checkpoints) all terminated on quota exhaustion. Under the
contract all eight are invalid and carry no label; a harness scoring
non-completing runs as $Y=0$ would have recorded eight fabricated task failures.

Across all five cases the common pathology is cross-layer confounding:
evaluator configuration, tool runtime, environment churn, future state, or
provider infrastructure is inadvertently recorded as evidence about agent
behaviour.

The architecture instantiates Section~\ref{sec:model} as three separated
channels. Online feature extraction is typed to accept only a
\texttt{TrajectoryPrefix} --- an immutable copy of the first $k$ steps holding
no outcome record --- so leakage is a type error rather than a code-review
question. Provider retries and physical attempts are handled strictly below
trajectory semantics, so a recovered 503 is invisible to behavioural features
while remaining fully logged. The evaluator runs after termination in a clean
state, resetting test files to the instance base commit before applying the
official test patch, so the agent cannot influence the tests that judge it.

\noindent\textbf{Reference invariants.} Our artifact enforces the following as
regression tests. These are the invariants \emph{this} artifact implements, not
a claim that they are universally necessary or sufficient.

\begin{quote}\small
\textbf{I1} Online prefix cannot access future trajectory information.
\textbf{I2} Online prefix cannot access $Y_{\text{success}}$.
\textbf{I3} Evaluation state is isolated from agent execution state.
\textbf{I4} Provider failures do not increment semantic failure features.
\textbf{I5} Infrastructure-invalid runs receive no $Y_{\text{success}}$.
\textbf{I6} Repository-change features are repository-scoped.
\textbf{I7} Raw trajectory artifacts are immutable and hashed.
\textbf{I8} Logical agent calls are distinct from physical provider attempts.
\textbf{I9} Restored continuations receive new identities and cannot overwrite
parents.
\end{quote}

The artifact ships 128 passing tests covering these invariants, including the
adversarial case E4, negative cases for test-command detection, and
provider-error classification. Every number here is regenerated by one
deterministic command requiring no paid API. E4 and E5 run anywhere; E1--E3
additionally need a local container runtime and one benchmark image.

\noindent\textbf{Minimum validity record.} The invariants are only auditable if
runs carry enough provenance to check them. For each evaluation run we suggest
recording at least: (1) validity status and, if invalid, the reason; (2)
evaluator and benchmark configuration and version; (3) the temporal scope of any
online features; (4) logical agent calls separately from physical provider
attempts and events; and (5) immutable run and checkpoint identifiers or hashes.
We offer these fields as a starting point for community discussion, not a
complete reporting standard.

\section{Discussion and Limitations}

\noindent\textbf{Limitations.} (1) These cases establish \emph{possibility and
mechanism}, not \emph{prevalence}; we make no estimate of how often such defects
occur in published harnesses. (2) The artifact is validated primarily for one
coding-agent / SWE-bench-style setting, and the invariants need evaluation on
other frameworks before being treated as general. (3) The provider events we
report are case-study evidence from one free-tier account; they are \emph{not}
estimates of any provider's service reliability. (4) \textbf{Real-provider
replay stability remains unmeasured}: every continuation we launched was
terminated by provider quota before executing a step, so we report no
replay-fidelity result and no divergence measurement. (5) We report no
predictor, scheduler, or large-scale agent-performance study, and no claim about
agent success rates. (6) Our invariants may be incomplete; passing them is
necessary for the validity conditions we state, not sufficient for validity in
general.

\noindent\textbf{Question for the community.} What minimum validity and
provenance information should accompany an agent benchmark result before that
result can be interpreted as evidence about agent reliability? Answering it is a
precondition for shared evaluation protocols and reusable artifacts in
multi-step agent evaluation, and the record above is our attempt at a concrete
starting point rather than a finished answer.

\section{Related Work}

Where prior work studies how agents fail, we study when an execution should
count as evidence about agent failure at all.
\citet{zhao2026failure} analyse the onset, evolution, and recovery of
coding-agent failures across a large set of complete trajectories;
\citet{ruan2026doomed} predict eventual failure from early rounds to abort
doomed episodes; and \citet{li2026early} derive online warning signals for
wasted computation. Each presupposes that the trajectory record faithfully
represents what happened --- the property we test. Complementary to these,
\citet{gonuguntla2026replay} show that static replay under a substituted model
scores a counterfactual world and use same-model controls to quantify replay
noise; we focus instead on cross-layer integrity between execution,
instrumentation, provider state, and evaluator output.
\citet{weidinger2025evalscience} argue for maturing an evaluation science for
generative AI with attention to validity and evaluation norms; we instantiate
those concerns as concrete, regression-tested failure cases in multi-step
coding-agent infrastructure. SWE-bench \citep{jimenez2024swebench} and its
human-validated subset \citep{openai2024swebenchverified} supply the benchmark
and evaluator methodology we instrument, and SWE-agent
\citep{yang2024sweagent} established the agent-computer interface such harnesses
build on. \citet{kapoor2024agentsthatmatter} identify methodological problems in
agent benchmarking including inadequate holdout and cost-blind comparison; our
scope is narrower, targeting measurement validity at layer boundaries. We do not
claim to be first to observe any individual defect; the contribution is
demonstrating them concretely under one abstraction and closing them with
enforced invariants.

\section{Conclusion}

Trustworthy agentic systems require trustworthy measurements, and in multi-step
evaluation the measurement apparatus is itself a layered system whose boundaries
can confound the variable being recorded. We demonstrated five controlled
cross-layer confounds, gave an architecture and an operational validity contract
that separate online trajectory state, provider telemetry, and offline
evaluation, and released an artifact enforcing nine regression-tested
invariants. The results are preliminary and methodological. We offer them as a
concrete starting point for a shared discussion about what an agent evaluation
harness must guarantee before its numbers can carry weight.
